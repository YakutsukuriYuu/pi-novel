# pi-novel

**用 Obsidian 维护小说，让 Pi 来写。所有内容都是普通 Markdown。**

人物、关系、世界观、规则、大纲、章节、时间线、伏笔、情感线、审稿与版本恢复，
全部是可以在 Obsidian 里直接读写、用双向链接串起来的 `.md` 文件。文件夹名是中文，
打开就能看懂。

不是一个独立聊天网站，也不包含模型服务：创作使用 Pi 当前的模型和凭据，
文件管理与校验不需要模型请求。

## 安装

需要 Node.js 22+ 和支持当前 Extension API 的 Pi（本版本在 **Pi 0.85.1** 上验证）。

```bash
pi install git:github.com:YakutsukuriYuu/pi-novel
```

已有 Pi 会话执行 `/reload`，或重启 Pi。插件不会自动创建书籍，也不改你的现有文件。

## 一个目录就是一本书

```text
~/Obsidian/小说/
├── 雨城/     ← 在这里启动 Pi，激活《雨城》
└── 铁塔/     ← 在这里启动 Pi，激活《铁塔》
```

- **激活只看当前目录**，不向上查找。在 `雨城/` 里启动就是《雨城》，在 `雨城/人物/` 里启动
  什么都不会激活 —— 子目录不继承父目录。
- 在已激活的目录里，**整棵目录树都属于这本书**。读写 `人物/林默.md` 照常，不需要额外操作。
- 两本书互相看不见对方的文件。

如果开在了小说的子目录里，插件会提醒你「应该在小说根目录启动」—— 只提醒，不会替你
去激活父目录。

## 你只说话，模型干活

**作者需要手输的命令只有两个：**

```text
/novel init [书名]     在当前文件夹激活（允许非空目录，不会覆盖已有文件）
/novel close           关闭本会话的管理保护
```

其余全部直接和模型说：

```text
「我们立项吧」                    「新建一章叫雨夜」
「按这个方案写」                  「这章可以了」
「加个人物叫林默」                「检查一下」
「概要把第三段改冷一点」          「把第 3 章挪到第 2 章前面」
「我写了个老张的笔记，收编成人物」  「撤销刚才那次修改」
```

需要你本人拍板的那几步（采纳、发布、确认、退回），模型会**弹一个确认框**，你点一下就行 ——
不必输命令，也不必记文件路径。**模型无法代替你批准任何东西。**

## 从一本新书开始

```bash
cd 我的小说
pi
```

```text
/novel init 雨城
```

它会在当前目录铺好骨架（都是空的，等着填），并列出它发现的、你自己写的笔记 ——
**那些不会被自动改动**。
非空目录也没问题：`.obsidian/`、附件、草稿都不会被碰。

然后说「我们立项吧」。模型会按固定顺序和你逐项确定：

| 顺序 | 内容 | 落在哪 |
| --- | --- | --- |
| 1 | **文风** | `设定/文风.md` |
| 2 | **背景** | `设定/背景.md` |
| 3 | **世界观** | `设定/世界观.md` |
| 4 | **世界规则** | `规则/世界规则.md` |
| 5 | **全书大纲** | `大纲/全书大纲.md` |

文风排第一是刻意的：调子不定，后面写的每一句话都是返工。

每一项的节奏是「先提问 → 给候选 → 等你选 → 才落盘」，不是一次抛问卷。写完会请你确认。

`novel_check` 随时报出立项进度（`缺失` / `空白` / `草稿` / `已确认`）。**不硬拦**你提前写正文，
但会告诉你还差什么。

## 写一章：先方案，后正文

这是本插件最核心的约束，**由工具强制，不是提示词约定**。

```text
你：第五章我想写雨夜追凶，林默第一次见到沈遥

模型：（只在对话里给方案，不落盘）
      我理解的方向是……三个可选处理……
      你倾向哪个？

你：2 好，但结尾别用追逐戏

模型：（仍在对话里）改成 XXX。要不要我把方案存进 方案.md？

你：存吧

模型：novel_new_chapter + novel_propose
      → 章节/0005-雨夜/方案.md 追加一节「## 方案 v1」

你：点确认框批准

模型：novel_write 写 正文.md   ← 到这里才允许
```

**在没有被批准的方案之前，`正文.md` 拒绝任何写入。** 强行写会被工具回绝：

```text
本章方案尚未被作者批准，不能写正文。
```

**`novel_propose` 只能往下追加** `## 方案 vN`，永远不会覆盖你写的「作者要求」和「作者批注」
段落 —— 这是结构上的保证，不是「请模型不要改」。

方案批准之后如果你又改了它（包括在 Obsidian 里直接改），**批准自动失效**，正文重新上锁。

## 你只管 md 文档

这本书的前端是 Obsidian，你直接用编辑器读写这些文件：

- **用 `[[双方括号]]` 连接**。正文里写 `[[人物/林默]]`，跳转、反向链接、关系图谱全部自动生效。
- **人物卡用 `aliases` 记绰号**，让 `[[老林]]` 也能链到同一张卡：
  ```yaml
  aliases: [老林, 林队]
  ```
- **文件随便重命名、随便移动**。引用记的是稳定编号，不是路径 —— 改名字不会破坏任何追溯链。
- **手写但还没纳入管理的笔记**，`novel_check` 会把它们列在 `unmanaged` 里，
  说一句「收编」就能补上 frontmatter 并移进规范目录（会弹确认框，因为那是在改你的文件）。

### 元数据

受管文档用 YAML frontmatter。Obsidian 会把它渲染成 **Properties 面板**，折叠显示、可筛选。

```yaml
---
id: 8f3a2b1c-...
kind: character
title: 林默
status: draft
aliases: [老林, 林队]
refs: [沈遥的编号]
sources: []
---
下列是正文……
```

`id` 是稳定身份，`sources` 也只记编号 —— **这是为了让重命名文件不破坏任何东西**。

## 文件结构

顶层 13 个目录，都是中文。目录按需创建，不为没有内容的对象批量生成空文件。

```text
我的小说/
├── AGENTS.md                    本书给 AI 的长期约定（可直接编辑）
├── 创作约定.md
├── 规则/                        世界规则 写作规则 禁忌
├── 设定/                        文风 背景 世界观 体系
│   └── 地点/  势力/  物品/  概念/
├── 人物/                        人物卡
│   └── 关系/                    初始关系
├── 大纲/                        全书大纲 分卷
│   └── 剧情线/
├── 章节/0001-雨夜/
│   ├── 方案.md                  ★ 写正文前的方案，须经作者批准
│   ├── 正文.md
│   └── 摘要.md                  绑定正文版本，采纳的前置条件
├── 当前状态/                     按时点切片
│   ├── 人物/0001-林默.md
│   └── 关系/0001-林默×沈遥.md
├── 伏笔/                        埋设与回收的账
├── 情感线/                      跨全书的关系轨迹
├── 时间线/                      客观事件编年
├── 审稿/  灵感/ 灵感/考据/  提案/
├── 导出/
└── .novel/                      管理元数据、事务记录、写锁
```

几处刻意的区分：

- **`情感线/` ≠ `当前状态/关系/`**：前者是设计（长期走向），后者是事实（某一章的样子）。
- **`时间线/` ≠ `当前状态/`**：前者记客观发生了什么，后者记人物*以为*发生了什么。
  两者的差值就是叙事张力 —— 合并它就丢了东西。

## 保护规则

- **草稿不等于正史**：`accepted` / `published` / `confirmed` 的内容要先由作者退回草稿才能改。
- **计划不等于事实**：方案、灵感、提案是想法，不是已经发生的事。
- **派生资料可追溯**：摘要、状态、事件、关系变化、审稿都记录来源编号与精确版本；
  正文一改，来源即过期，`novel_check` 会报出来。
- **采纳需要当前摘要**：正文必须有绑定当前版本的摘要才能被采纳 —— 防止「正文改了、
  摘要还是旧的」被随手通过。
- **变更有记录**：每次写入都是事务，保留前后完整 Markdown，可以整体回滚。
  撤回时若发现有后续或外部修改，**拒绝执行**而不是覆盖。
- **外部编辑可发现**：你随时用 Obsidian 改文件都不会被静默吞掉，已受保护的内容一旦被改动
  会被检查发现。

## 安全边界

打开小说时，**默认拒绝**：不在白名单里的一律拦下。

| | 工具 |
| --- | --- |
| **放行** | `read` `grep` `find` `ls` `ffgrep` `fffind` `web_search` `web_fetch` + 17 个 `novel_*` |
| **拦下** | `bash` `edit` `write` `powershell`、`subagent`、`mcp` `mcpScript`、以及**一切未知工具** |

保留 `bash`/`edit`/`write` 会让模型的每次落盘都绕过内核 —— 索引、版本追踪、事务记录、
状态机全部失效。所以模型只能通过 `novel_*` 写文件。

用**白名单**而不是黑名单，是因为失败模式差得太远：

- 白名单漏一项 → 某个只读工具不能用。烦，但无损，改一行就好。
- 黑名单漏一项 → 模型绕过保护改坏原稿，而且**事务系统记不到**，等于没有回滚点。

实测过的三个「朴素黑名单会漏掉」的口子：`subagent` 派出的子代理自带 `bash`/`edit`/`write`；
`ast_grep_replace` 能改文件但名字里没有 `write`；`pi_lens_activate_tools` 一句话就能把它激活。

### 只读工具不能出项目

`read` / `grep` / `find` / `ls` / `ffgrep` / `fffind` 的路径参数被限制在**本书目录之内**。
`../别的书/x.md`、绝对路径、`~/x` 都会被拦下，项目内指向外部的符号链接也会被发现。

`web_search` / `web_fetch` 按 URL 工作，不受此限制。

### 配置

```json
// ~/.pi/agent/pi-novel.json    （可选，插件不会主动创建）
{
  "additionalAllowedTools": [],
  "allowReadOutsideProject": false
}
```

- `additionalAllowedTools`：额外放行的工具名。**只能追加**，无法缩减内置白名单。
  加什么就完全信任什么 —— 插件不检查「你加的是不是写工具」，因为那需要一张
  「已知能写」的清单，而清单永远不全。
- `allowReadOutsideProject`：设为 `true` 时关闭只读工具的项目边界。

配置在会话开始时读一次，改完重开生效。`novel_check` 会报出当前生效的边界，
你可以随时自查：

```json
"toolAccess": {
  "builtinReadonly": ["read", "grep", "find", "ls", "ffgrep", "fffind", "web_search", "web_fetch"],
  "extraAllowed": [],
  "readOutsideProject": false,
  "configProblem": null
}
```

配置写坏了会退回默认值继续，但会在启动和检查里报出来 ——「以为加了工具其实没生效」
比直接报错难查得多。

## 工具清单

模型调用，你不必记。

| 工具 | 作用 |
| --- | --- |
| `novel_check` | 一站式现状：结构问题、立项进度、每章方案状态、未纳入管理的笔记、当前边界 |
| `novel_catalog` / `novel_read` | 分页检索 / 读取正文与版本 |
| `novel_context` | 列出本章该读哪些文件（只是清单，不是内容） |
| `novel_history` | 修改历史 |
| `novel_create` | 新建设定类文档 |
| `novel_new_chapter` | 建章，同时生成 方案 / 正文 / 摘要 |
| `novel_propose` | **只追加**一轮章节方案 |
| `novel_write` / `novel_patch` / `novel_rename` | 整篇替换 / 局部修改 / 改标题 |
| `novel_summary` | 保存章节摘要并绑定正文版本 |
| `novel_authorize` | **请求作者授权**（弹确认框） |
| `novel_adopt` | 收编你手写的裸 md（弹确认框） |
| `novel_reorder` | 重排章节（弹确认框） |
| `novel_recover` | 撤销某次修改（弹确认框） |
| `novel_export` | 导出已采纳章节 |

会弹确认框的四个标了 `executionMode: 'sequential'` —— pi 默认并行执行一条消息里的多个
工具调用，而并发确认框会把界面卡死。串行是必需的，有测试锁着。

## 明确的边界

**这不是操作系统沙箱。**

- 你手动编辑、`!` 命令、其他进程、其他插件仍然可以改文件。插件的保护针对**模型**。
- 只读工具的边界是路径检查，不是文件系统隔离。
- 文件哈希与写锁保护协作进程，不提供对任意外部进程的 compare-and-swap。
  保存时避免在其他编辑器同时改同一文件。
- 插件不会自动发现剧情漏洞，不推断完整依赖图，不提供多人协作或可视化 UI。
- `novel_context` 是路径清单，不是「已经读完资料」；内容由模型按需读取。

请保持正常备份。事务记录能恢复插件自己的写入，但**不替代你的备份习惯**。

```bash
npm ci --ignore-scripts

```

测试覆盖：非空目录激活、收编、方案批准门槛（含拒绝路径）、只读边界（含符号链接穿透）、
工具白名单、配置容错、来源编号绑定、事务恢复、路径穿越、符号链接/硬链接拒绝、

测试不调用在线模型、不读取你的模型密钥、不改真实小说。

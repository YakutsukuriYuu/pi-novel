# 恢复

## 什么时候会用到

- 改错了想退回去
- 上一次 Pi 崩了，留下未完成的事务
- 看到「Project locked」
- 你在 Obsidian 里改了什么，想确认它有没有出问题

大部分情况下，**先跑一次 `novel_check`**（跟模型说「检查一下」）就知道该做什么。

## 事务是怎么记的

每次写入都是一个事务。文件落在：

```text
.novel/transactions/<时间戳>-<随机ID>.md    已完成
.novel/pending/<时间戳>-<随机ID>.md         进行中
```

每个事务记录里含**每个涉及路径的完整前后 Markdown**：

```yaml
---
id: 1789747570061-3f2a...
kind: transaction
title: 新建 章节 雨夜
status: committed      # 或 pending / rolled-back
changes:
  - path: 章节/0001-雨夜/正文.md
    before: null       # null 表示当时不存在
    after: |-
      ---
      id: ...
      ---

      # 雨夜
---
```

写入的顺序是刻意的：

1. 先写 `pending` 标记
2. 逐个原子替换（临时文件 + rename）
3. 归档到 `transactions/`
4. 删掉 `pending` 标记

**中途崩在 2 和 3 之间，会留下 `pending` 标记。** 这时插件会拒绝继续写入：

```text
有未完成的事务；先让作者撤销它（novel_recover），再继续写入。
```

这是有意的 —— 未完成的事务必须先被处理，不能被当成正常状态继续往上叠。

## 撤销一次修改

对模型说「撤销刚才那次」，或者指名事务 ID。

会回滚**该事务涉及的所有文件**，恢复到修改前的原文（不是重做，是还原）。

不带 ID 时回滚最近一次。

### 什么情况下会拒绝

回滚前插件会逐个核对每个文件的当前状态。**只要有一个文件既不是「改后」也不是「改前」，
就拒绝执行**：

```text
Recovery conflict: 章节/0001-雨夜/正文.md; preserve external edits first.
```

意思是：这个文件在你那次修改之后又被动过了（可能是你在 Obsidian 里改的，
也可能是另一次插件操作）。**插件不会覆盖它** —— 你的后续编辑比「回到过去」更重要。

遇到这个：

1. 先用 `novel_history` 看清楚有哪几次修改
2. 用 `novel_read` 看当前内容，判断你想保留什么
3. 如果确实要退，先手工把你后来改的内容记下来，或者用 git 之类的工具

**插件不提供「强制覆盖」选项。** 会覆盖你手写内容的功能不该存在。

## 「Project locked」

写锁是 `.novel/lock/` 这个目录。同一时刻只允许一个写入者：

```text
Project locked. Stop other writers; see docs/recovery.md before manually removing .novel/lock.
```

正常情况下锁在操作结束后自动释放，你不需要关心。

**只有一种情况会看到它：某个 Pi 进程崩了，锁没释放。** 处理步骤：

1. **确认没有别的 Pi 正在写这本书。** 检查有没有别的终端、别的窗口开着这个目录。
   锁是跨进程的，不是跨进程安全的写保护 —— 两个进程同时写会互相覆盖，这才是锁要防的事。
2. 确认没有了之后，删掉锁目录：
   ```bash
   rm -rf /path/to/小说/.novel/lock
   ```
3. 跑一次检查。

`.novel/lock/owner.md` 里记着占锁的 PID 和开始时间，可以先看一眼：

```text
# Active writer

PID: 22574
Started: 2026-09-19T02:09:33.000Z
```

`kill -0 22574` 能判断那个进程还在不在。

## 你在 Obsidian 里改了什么

插件**不阻止**你改任何文件 —— 它如实记录，不假装。

| 你改的 | 结果 | 怎么处理 |
| --- | --- | --- |
| 草稿 | 没有影响 | 继续写 |
| `accepted` / `published` / `confirmed` 的正文 | 检查报「受保护内容被外部改动」 | 说「退回草稿」，重新确认后再采纳 |
| 已批准的章节方案 | 批准自动失效，正文重新上锁 | 重新讨论方案，再批准一次 |
| frontmatter 的 `status` | 检查发现摘要没绑定当前版本 | 重新保存摘要，或退回去 |
| 删了文件 | 检查报「找不到」 | 恢复文件，或接受它已经不在 |
| 改了文件名 | 不影响任何引用（来源记的是编号） | 无需处理 |

最后一行是本协议最重要的一条：**引用记编号不记路径**，所以重命名和移动文件永远安全。

## 遇到坏掉的 Markdown

`novel_check` 会逐份报告解不开的文件。常见原因：

- **没有 frontmatter**：作者手写的笔记。说「收编」纳入管理，或放着不管（插件会跳过它，
  不会因此崩掉扫描）。
- **YAML 写坏了**：手工编辑时缩进或引号出错。用编辑器修好，或者从历史事务里取回原文。
- **缺少必填字段**：`id` / `kind` / `title` / `status` 有一个丢了。

这些都不会让插件停止工作 —— 坏文件被跳过并报告，其余照常。**写入不受影响**，
除非坏的是你正要写的那一份。

## 备份

事务记录是**插件自己的写入历史**，它不替代备份：

- 它只记插件写的东西。你在 Obsidian 里的直接编辑不在其中。
- 它没有自动清理策略，会随写作一直增长。想删旧的可以手工删 `.novel/transactions/`。
- 它和小说放在同一个目录里。整个目录一起丢（误删、磁盘坏了）的话，它也跟着丢。

**建议把小说目录放进 git。** 那是真正能回到任意时间点的东西，
而事务记录只覆盖插件自己的操作。`.novel/pending/` 和 `.novel/lock/` 已经在
`init` 生成的 `.gitignore` 里了。

## 插件不做什么

- 不做全目录的断电级事务。逐文件原子替换 + 日志能恢复进程中断，但不宣称断电安全。
- 不提供对任意外部进程的文件系统级 compare-and-swap。保存时避免在其他编辑器同时改同一文件。
- 不自动「猜测修好」坏掉的文件。它报告问题，决定权在你。
- 不提供强制覆盖。回滚遇到冲突就停下。

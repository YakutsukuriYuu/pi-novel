# 小说创作与管理

作者用大白话跟你说话，你负责把流程走完。**除了 `/novel init`、`/novel migrate`、`/novel close`，
作者不需要、也不应该被要求输入任何命令** —— 也不要让他记文件路径。

这本书的前端是 **Obsidian**：作者会直接用编辑器读写这些 Markdown，而且只维护这些 md 文件。

## 一个目录就是一本书

小说模式只在**恰好那个目录**里激活，子目录不继承父目录。
所以你能读到这份 Skill，就说明当前目录就是小说根。

如果作者说“小说模式没生效”“检查不到项目”，很可能他在子目录里启动了 Pi。
告诉他回到小说根目录重新启动 —— **不要试图拿父目录的项目去操作子目录**。

## 立项：新项目的第一件事

按顺序与作者逐项确定。**每项都要他明确答复后才落盘。**

1. `设定/文风.md` — **第一个**。文风不定，后面写的每一句话都是返工。
2. `设定/背景.md` — 时代、地理、社会。
3. `设定/世界观.md` — 世界怎么运转。
4. `规则/世界规则.md` — 硬约束与上限。
5. `大纲/全书大纲.md` — 有了前四项才轮得到排事件。

每项的节奏：**先提问 → 给 2-3 个候选 → 等他选 → 才写文件**。不要一次抛出问卷，不要替他决定。
写完用 `novel_authorize` 请求确认。五项完成前不要开始写正文。

## 写章节：先方案，后正文

这是硬性流程，工具会拒绝跳过。

1. 作者提出写章节 → **先在对话里给方案，一个工具都不要调**。
2. 方案包含：本章目标、场景、出场人物、关键事件、情绪曲线、结尾钩子。
3. 与他讨论，可以多轮。**他没说「记下来」之前不要落盘。**
4. 他说记下来 → `novel_new_chapter`（如果还没建）+ `novel_propose` 追加。
   `novel_propose` **只能往下追加** `## 方案 vN`，永远不会覆盖他写的
   「作者要求」和「作者批注」段落 —— 这是结构上的保证。
5. 他说可以了 → `novel_authorize('confirm', 方案路径)`，会弹确认框让他点。
6. 批准之后才允许 `novel_write` 写正文。提前写会被拒绝，**拒绝时不要试图绕过**，
   回到方案讨论上去。

## 作者授权：`novel_authorize`

采纳、发布、确认、退回只能由作者决定。模型发起 `novel_authorize`，
终端会弹确认框，**他点了才算数**。你无法自己批准任何东西。

几条纪律：

- **一次只问一件事**，并且只在这件事真的做完了的时候问。
- **他拒绝了就停下**，不要换种说法再问，不要反复弹窗。
- 不要为了「顺便确认一下」而滥调它。
- 永远不要说「已获得作者同意」——除非你确实拿到了工具的返回结果。

## 工具

| 工具 | 用途 |
| --- | --- |
| `novel_check` | 一站式的现状：结构问题、立项进度、每章方案状态、**还没纳入管理的笔记** |
| `novel_catalog` | 分页检索；只给路径、编号、状态，不含正文 |
| `novel_read` | 读正文与 revision；`nextOffset` 非空就要继续读 |
| `novel_context` | 列本章该读哪些文件（只是清单，不是内容） |
| `novel_history` | 修改历史，供撤销时引用事务号 |
| `novel_create` | 新建设定类文档 |
| `novel_new_chapter` | 建章，同时生成 方案 / 正文 / 摘要 |
| `novel_propose` | **只追加**一轮章节方案 |
| `novel_write` | 整篇替换正文；必须回传刚读到的 `expectedRevision` |
| `novel_patch` | 局部替换，润色首选 |
| `novel_rename` | 改标题，编号不变 |
| `novel_summary` | 保存章节摘要并绑定正文版本 |
| `novel_authorize` | **请求作者授权**（弹确认框） |
| `novel_adopt` | 把作者手写的裸 md 纳入管理（弹确认框） |
| `novel_reorder` | 重排章节（弹确认框） |
| `novel_recover` | 撤销某次修改（弹确认框） |
| `novel_export` | 导出已采纳章节 |

## 作者手写的文件

他会直接在 Obsidian 里写笔记。`novel_check` 的 `unmanaged` 字段就是这些文件。

他说「我写了个东西」或发现某份笔记没被管理时，用 `novel_adopt` 收编：
补 frontmatter、分配编号、移进规范目录。**会弹确认框**，因为那是在改他的文件。

`documents()` 会跳过解不开的文件，所以一份没有 frontmatter 的笔记不会让扫描崩掉 ——
这也意味着**它不会出现在 catalog 里**，必须靠 `unmanaged` 发现。

## Obsidian 协作

- **不用 write / edit / bash 改小说文件。** 工具集里也没有这些，是刻意的。
- 正文里引用其他笔记写 `[[双方括号]]`，例如 `[[人物/林默]]`，让他的图谱和反向链接生效。
- 人物卡的 frontmatter 里维护 `aliases`，让绰号也能链到同一张卡：
  `aliases: [老林, 林队]`。
- `refs` 与 `sources` **只能用稳定编号**（如 `人物-8f3a…`），绝不能用路径 ——
  他会随手重命名文件和拖动文件夹。
- 人读的来源写进正文（`依据：[[章节/0001-雨夜/正文]]`），机器校验的放 frontmatter。
- 顶层目录：`规则/ 设定/ 人物/ 大纲/ 章节/ 当前状态/ 伏笔/ 情感线/ 时间线/ 审稿/ 灵感/ 提案/ 导出/`

## 事实与权限

- 草稿不是正史。`accepted` / `published` / `confirmed` 的内容要先由作者退回草稿。
- `方案` / `灵感` / `提案` 是想法，不是已经发生的事实。
- `摘要` / `状态` / `事件` / `关系变化` / `审稿` 是派生资料，可信度取决于来源版本是否仍然一致。
- 区分四种知识：人物知道、人物误解、读者知道、作者秘密。**作者的秘密不等于人物知道的事。**
- 状态记录按章节存放，不要用后一章的知识写前一章。
- `novel_check` 只查结构与版本，不证明语义一致。

## 收尾

正文实质变化后用 `novel_summary` 保存基于最终版本的摘要 —— 没有当前摘要，他无法采纳这一章。
视变化更新本章的事件、人物状态、关系变化和伏笔。纯讨论不写文件。
